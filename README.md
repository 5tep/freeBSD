Переход с одной системы фильтрации на другую (ipfw -> pf) и мажорное обновление ОС (9.2 -> 14.2) — это операция с высоким риском. Ошибки здесь означают, что абоненты останутся без интернета или без ограничений скорости.

Вот пошаговый план тестирования (QA), который позволит проверить систему **до** пуска живых людей.

---

### Этап 0. Подготовка и статический анализ

Перед тем как запускать биллинг, проверим, что сервер вообще готов.

1. **Проверка синтаксиса PF:**
```bash
pfctl -nf /etc/pf.conf

```


*Ожидаемый результат:* Пустой вывод (тишина). Если есть ошибки — исправляем.
2. **Проверка прав доступа скриптов:**
Убедитесь, что `OnConnect` и `OnDisconnect` исполняемые.
```bash
chmod +x /etc/rscriptd/OnConnect
chmod +x /etc/rscriptd/OnDisconnect
chmod +x /etc/rscriptd/GetSpeed
chmod +x /etc/rscriptd/GetUpSpeed

```


3. **Загрузка модулей ядра:**
```bash
kldstat | grep -E 'pf|dummynet'

```


*Ожидаемый результат:* Видим `pf.ko` и `dummynet.ko`.

---

### Этап 1. Ручное тестирование скриптов ("Сухой прогон")

Самый важный этап. Мы притворимся биллингом и запустим скрипты вручную из консоли сервера.

**Тестовые данные:**

* Логин: `testuser`
* IP: `172.16.32.100` (выберите свободный IP из вашей user_net)
* ID: `555`
* Деньги: `100`

**1. Тест подключения (OnConnect)**
Запускаем команду:

```bash
/etc/rscriptd/OnConnect testuser 172.16.32.100 555 100

```

*Если скрипт отработал без ошибок, проверяем состояние системы:*

* **Проверка правил PF (Anchor):**
```bash
pfctl -a ubilling/testuser -s rules

```


*Ожидаемый результат:* Вы должны увидеть правило с `dnpipe`. Примерно так:
`pass quick on ix1 inet from 172.16.32.100 to any dnpipe(8656, 656)`
*(Числа в dnpipe зависят от ID: 555+8101 и 555+101)*
* **Проверка труб (Pipes):**
```bash
dnctl pipe show

```


*Ожидаемый результат:* Вы должны увидеть два пайпа (один на вход, один на выход) с установленной скоростью (которую вернул `GetSpeed`).
* **Проверка файла авторизации:**
```bash
cat /etc/stargazer/dn/testuser

```


*Ожидаемый результат:* Файл существует, внутри скорость и ID.

**2. Тест отключения (OnDisconnect)**
Запускаем команду:

```bash
/etc/rscriptd/OnDisconnect testuser 172.16.32.100 555 100

```

* **Проверка:**
1. `pfctl -a ubilling/testuser -s rules` -> **Пусто** (правил нет).
2. `dnctl pipe show` -> **Пайпов 656 и 8656 нет**.
3. `pfctl -t block_users -T show` -> **IP 172.16.32.100 есть в списке**.
4. `/etc/stargazer/dn/testuser` -> **Файл удален**.



---

### Этап 2. Интеграционное тестирование (rscriptd)

Теперь проверяем, слышит ли демон `rscriptd` команды от биллинга.

1. Запустите `rscriptd` (если не запущен):
```bash
service rscriptd start
tail -f /var/log/rscriptd.log

```


2. Идите в веб-интерфейс Ubilling -> Профиль пользователя `testuser`.
3. Нажмите кнопку **"Подключить"** (или сбросить сессию).
4. Смотрите лог `/var/log/rscriptd.log`.
*Ожидаемый результат:* Появление записи `Execute /etc/rscriptd/OnConnect ...`.
5. Проверьте `pfctl` и `dnctl` (как в этапе 1). Они должны были создаться автоматически.

### Этап 3. Функциональное тестирование (Трафик)

Подключите реальный ноутбук или виртуалку в порт LAN (ix1) и настройте на нем IP `172.16.32.100`.

**Сценарий 1: Доступ есть (User Active)**

1. Убедитесь, что пользователь "Подключен" в биллинге.
2. На ноутбуке: `ping 8.8.8.8`. (Должен идти).
3. На ноутбуке: `nslookup google.com`. (DNS должен работать).
4. **Speedtest:** Запустите `speedtest-cli` или iperf.
* *Критерий успеха:* Скорость должна соответствовать тарифу пользователя (проверьте, не перепутаны ли Upload/Download). Если перепутаны — поменяйте местами аргументы в `dnpipe (OUT, IN)` в скрипте `OnConnect`.



**Сценарий 2: Доступ заблокирован (User Blocked/Disconnected)**

1. В биллинге нажмите "Отключить" или выставьте баланс в минус.
2. На ноутбуке: `ping 8.8.8.8`. (Должен пропасть).
3. Откройте браузер и перейдите на `http://neverssl.com` (любой HTTP сайт).
* *Критерий успеха:* Должен сработать редирект (RDR) на заглушку "Пополните счет" (порт 81).
* *Диагностика:* Смотрим таблицу блокировок: `pfctl -t block_users -T show`.

### Этап 4. Нагрузочное тестирование и рестарт

1. **Массовые операции:**
Попробуйте в Ubilling нажать "Перестроить/Сбросить всех". Это вызовет лавину запусков скриптов.
* Следите за нагрузкой CPU (`htop`).
* Убедитесь, что `rscriptd` не падает.


2. **Рестарт сервера (Reboot):**
Перезагрузите FreeBSD.
* После загрузки: `pf` правила загрузились?
* *Важный нюанс:* После ребута NAS "пустой" (нет пользовательских якорей). Биллинг (Stargazer/Ubilling) должен сам перепослать сигнал OnConnect для активных юзеров. Обычно это происходит при старте Stargazer, или нужно вручную пнуть процесс. Проверьте этот момент: восстанавливается ли доступ у юзеров после ребута NAS без ручного вмешательства.



---

### Чек-лист перед запуском в продакшн:

* [ ] `pf.conf` валиден и загружен.
* [ ] Скрипты `OnConnect`/`OnDisconnect` имеют права `+x`.
* [ ] Логирование в `/var/stargazer/allconnect.log` идет.
* [ ] Шейпер режет скорость корректно (Download/Upload не перепутаны).
* [ ] Редирект должников работает.
* [ ] DNS ходит.
* [ ] `rscriptd` добавлен в автозагрузку (`/etc/rc.conf`).

**Полезные команды для дебага в процессе:**

```bash
# Смотреть что происходит в PF в реальном времени (tcpdump на pflog0)
tcpdump -n -e -ttt -i pflog0

# Смотреть счетчики правил конкретного юзера (идет ли через них трафик)
pfctl -a ubilling/LOGIN -v -s rules

```
